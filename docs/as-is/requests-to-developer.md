# 【現行】開発者への要請と提案

> 【現行】作り直す前の現行サイトについての文書。新しい設計は `docs/to-be/` を見る。

UI 改善の担当から GAS 側（サーバーとスプレッドシート）の担当への依頼をまとめる。
根拠は `docs/as-is/site-analysis.md` と `docs/as-is/data-model.md`。

> 2026-11-21 更新: 現行の改修ではなく GAS で一から作り直す方針になった（`docs/to-be/design.md`）。この文書の B と C の提案は設計書に取り込んだ。依頼者に確認が要るのは A1（味わいの分類の候補）、A4（運用の前提）と、設計書の「9. 決めて欲しいこと」。A2、A3 は作り直す場合は不要になる。

優先度
- A: UI 改善を進める前に回答が欲しい
- B: UI 改善と並行して対応して欲しい
- C: 余裕があれば検討して欲しい

## A. 先に確認したいこと

### A1. families の仕様
- 値の候補の一覧（例: フルーティー、柑橘、チョコ、ナッツ …）と、表示したい並び順
- 1つの豆に付ける数の上限
- 今の公開版の `getMenuData` は `families` を返していない。返す予定の時期
- 依頼
  - 値がない豆は `families: []` で返して欲しい（画面は空配列を前提に作る）

### A2. submitOrder の仕様
- 戻り値 `total` は送料込みか
- サーバー側で次を検証しているか
  - 種類数の上限、合計グラムの上限、1種類の最小量と刻み
  - 存在しない豆の名前、非表示の豆
- 失敗時の扱い
  - 画面は `err.message` をそのまま出している。利用者に見せてよい文言で `throw` しているか

### A3. 参照用の資料
- サーバー側のコード（.gs）
- スプレッドシートの構成（タブ名と列）。値を伏せた写しで構わない

### A4. 運用の前提
- 郵送のときの住所、手渡しの日時は今後も LINE で聞く運用でよいか
- 1種類あたりの量を 300g までにしているのは意図どおりか（合計の上限は 450g）

## B. 並行して対応して欲しいこと

### B1. 二重注文の防止
- 現状、送信成功の後に画面を触ると注文ボタンが再び押せる。画面側は直すが、サーバー側でも防いで欲しい
- 提案
  - 画面が送信ごとに `orderId`（ランダム文字列）を付けて送る。サーバーは同じ `orderId` を2回目以降は記録せず、1回目と同じ結果を返す
  - 書き込みは `LockService.getScriptLock()` で囲み、同時の注文で行が壊れないようにする

### B2. 設定値を getMenuData で返す
- 案内文や郵送ボタンの「¥300」「3種類・合計450g」は HTML に直書きで、シートの設定を変えると表示とずれる
- 画面側はすべて MENU の値から作るように直す。追加で次の値を返して欲しい
  - `maxPerItem`: 1種類あたりの上限（今は画面に 300 が直書き）
  - 受け取り方法の一覧（例: `[{key: "hand", label: "手渡し", fee: 0}, {key: "post", label: "郵送", fee: 300}]`）。今の `shipping` は残してよい
  - 案内枠の文言をシートで編集したい場合はその文言（不要なら画面で設定値から組み立てる）

### B3. 豆を ID で識別する
- 今は豆の名前で注文を結び付けている。名前を直すと、直す前に開いた画面からの注文が失敗するか、別の豆に結び付く可能性がある
- 提案
  - 各豆に変わらない `id` を持たせて `getMenuData` で返し、`submitOrder` の `items` に `id` も入れて送る。移行の間は `name` も送り続ける

### B4. 公開しなくてよい関数を非公開にする
- `testMenuData` が外から呼べる状態になっている（呼ぶと `null` が返る）
- 不要なら削除、残すなら関数名の末尾に `_` を付けて非公開にする

## C. 余裕があれば検討して欲しいこと

### C1. 初回表示を速くする
- 今は画面を開いた後に `getMenuData` を呼び、表示まで1.5秒前後かかる
- 提案（効果の大きい順）
  - `doGet` で `HtmlService.createTemplateFromFile` を使い、メニューの JSON を HTML に埋め込んで返す。画面は開いた時点でメニューを出せる
  - `CacheService` でメニューを数分キャッシュし、シート編集時（`onEdit`）に消す
- 画面側は、埋め込みがあればそれを使い、なければ `getMenuData` を呼ぶ作りにする

### C2. 売り切れを表示できるようにする
- 今は非表示の豆が返らない（`order` 6 が欠番）。「今週は売り切れ」と見せたい場合は、行を返したうえで `soldOut: true` を付けて欲しい

### C3. 焙煎度の段階の名前
- 焙煎度は 1〜7 の数値だけで、段階の名前（浅煎り、中煎り …）がない。名前があれば画面に出せる
- 画面の「浅め」の絞り込みは 1〜2 を対象にしているが、今のメニューに該当する豆がなく、押すと0件になる。区切り（浅め/中/深め）の境目を決めて欲しい

### C4. 受付番号を返す
- `submitOrder` の戻り値に受付番号（例: 日付 + 連番）を足せば、完了画面に出して LINE でのやり取りに使える

### C5. 画面の置き場所（将来）
- 画面の最上部に出る Google の警告バーは GAS の外枠が出すので、HTML 側では消せない
- 気になる場合は、画面だけ GitHub Pages などに置き、GAS は `doGet` / `doPost` で JSON を返す形に分けられる。スプレッドシートで管理する仕組みは変わらない
- 画面側はサーバーを呼ぶ処理を1か所にまとめておき、移す場合の変更を小さくする
