# 技術検証の結果

技術検証の結果。T1-1（システムの自己更新）〜T1-4（Web アプリの動作）の結果を、確かめたこと、結果、設計への影響の形で残す。Web アプリの URL とデプロイ ID は書かない。

## 用語

説明の元は `docs/to-be/glossary.md`。

| 用語 | 意味 |
|---|---|
| ローダー | スプレッドシートに紐づくスクリプト。外から呼べる関数（入口）、`_コード` タブからの読み込み、「システムを更新」と「前のバージョンに戻す」の処理、初期のコードを持つ。テンプレートのコピーの後は変えない。「システムを更新」でも変わらないので、ローダーの中の処理に不具合があっても、「システムを更新」では直せない |
| 入口 | ローダーの中で、GAS が直接呼ぶ関数。メニュー OUCA、管理タブのボタン、トリガー、Web アプリ、画面からの呼び出しは、すべてここから入る |
| バンドル | システムのコード（モジュールと画面の HTML）を1つにまとめたファイル。GitHub のリリースに置き、「システムを更新」で `_コード` タブに取り込む |
| モジュール | バンドルのうち、サーバーで動く処理の部分。ローダーが `_コード` タブから文字列として読み込み、動かせる関数に変えて（評価して）呼ぶ |
| 初期のコード | ローダーの中に最初から入れておくバンドル。`_コード` タブに最初のバンドルを入れるときと、`_コード` タブが読めないときに使う |
| `_コード` タブ | バンドルを保存する、非表示のタブ |
| 保存場所（A、B） | `_コード` タブの中で、バンドルを1つずつ入れる2か所。片方に今のシステムのバージョンが入る。もう片方には、1つ前のシステムのバージョンがあればそれが入る（「前のバージョンに戻す」の戻す先）。「システムを更新」は、使っていない方に新しいシステムのバージョンを書く |
| 使用中の指定 | A と B のどちらの保存場所のバンドルを動かすかを書いた設定。スクリプトのプロパティに置く。スクリプトのプロパティはテンプレートのコピーに引き継がれないので、同じ内容を `_コード` タブのセルにも書く。2か所が違うときは、スクリプトのプロパティの方に従う。「システムを更新」と「前のバージョンに戻す」は、この指定を書き換えて切り替える |
| 読み込み方式 | システムのコードを `_コード` タブに置き、ローダーが動くたびに読み込んで動かす方式。スクリプトが自分の中身を書き換える方式が成り立たなかったので、T1-1（システムの自己更新）で選んだ |
| リリース | GitHub の機能。コードのある時点に番号（タグ。v1.3.0 など）を付け、バンドルを添付して出す。オーナーは「システムを更新」で、最新のリリースのバンドルを取り込む |
| テンプレート | デザイン担当が作る、初期設定済みのスプレッドシート。オーナーは「コピーを作成」でこれを複製して、本番のスプレッドシートにする |
| テスト用スプレッドシート、テスト用スクリプト | デザイン担当が持つ、ダミーデータだけのスプレッドシートと、それに紐づくスクリプト。`npm run push:test` でローダーを送り、GAS の上の動きを確かめる |
| 外から呼べる関数 | GAS では、スクリプトの一番外側に書いた関数を、メニュー OUCA、ボタン、トリガー、画面から名前で呼べる。このアプリの Web アプリは誰でも開ける設定なので、知らない人も画面からこれらの関数を呼べる。名前の末尾が `_` の関数は、画面からは呼べない |
| 持ち主 | Google ドライブの上でスプレッドシートやスクリプトを持っている人。Google の画面では「オーナー」と出る。本番では、お店のオーナーが持ち主になる |
| スクリプトのプロパティ | スクリプトごとに値を保存しておける、GAS の設定の置き場。シートには出ず、テンプレートのコピーには引き継がれない |
| トリガー | 決まったとき（シートを開いた、編集した、決めた時刻になった）に、関数を自動で動かす GAS の仕組み |
| シンプルトリガー | 関数に決まった名前（`onOpen`、`onEdit`）を付けるだけで動くトリガー。承認の前でも動くが、できることが限られる |
| インストール型のトリガー | スクリプトが作って登録するトリガー。作った人の権限で動く。テンプレートのコピーには引き継がれないので、初期設定で作る。決めた時刻や間隔で動くものを「時間主導のトリガー」と呼ぶ |
| Web アプリ | スクリプトを URL で開けるページにしたもの。お客さんが注文する画面になる |
| デプロイ | Web アプリを作る操作と、作った結果のこと。このアプリでは、オーナーが初回に作り、作り直さないので、URL は変わらない（管理画面を2つ目のデプロイで出すかは #54 で決める） |
| `google.script.run` | Web アプリの画面（ブラウザ）から、サーバーの関数を呼ぶ GAS の仕組み。呼べるのは外から呼べる関数だけ（名前の末尾が `_` のものは除く） |
| 承認 | スクリプトが初めて権限の要る処理をするときに出る画面で、持ち主が権限を許可すること |
| マニフェスト | スクリプトの設定ファイル（`appsscript.json`）。スクリプトが求める権限の範囲や、Web アプリの設定を書く。ローダーの側にあるので、「システムを更新」では変えられない |
| 権限の範囲（`oauthScopes`） | スクリプトが使ってよい Google の機能の一覧（スプレッドシートの読み書き、メールの送信など）。マニフェストに書き、持ち主が承認の画面で許可する |
| キャッシュ（`CacheService`） | GAS の一時的な保存の場所。読み込みを速くすることと、二重送信を見分けることに使い、最長6時間で消える |
| `LockService` | ロックを取る処理どうしが、同時に動かないようにする GAS の仕組み。注文と「システムを更新」で使う |
| Apps Script API、既定の Cloud プロジェクト | Apps Script API は、スクリプトの中身やデプロイを外から変える Google の仕組み。スクリプトごとに自動で作られる Cloud プロジェクト（既定の Cloud プロジェクト）では、この API を有効にできなかった（T1-1） |
| メニュー OUCA | スプレッドシートの上に出る、このシステムのメニュー。「OUCA ▸ メニューを公開」のように、中の項目を押して操作する。初期設定の前は「初期設定」など少しの項目だけが出る |
| T 番号、D 番号 | ワークプランのタスクの番号（T1-2 など）と、ユーザーに決めてもらうことの番号（D-1 など）。対応は `work-plan.md` §3、§4 にある。文書の中では、初めて出る位置でタスクの名前を添える |
| § | 文書の節の番号。「`delivery-flow.md` §5.3」は、受け渡しの文書の 5.3 の節を指す |

### 7. 既定の Cloud プロジェクトのままで Apps Script API を呼べる

- 確かめたこと
  - `UrlFetchApp` と `ScriptApp.getOAuthToken()` で Apps Script API を呼べるか。呼べない場合に、Cloud プロジェクトの作成をオーナーに頼む必要があるか
- 結果
  - 呼べなかった（2026-11-21、個人の Gmail アカウントのテスト用スクリプト）
  - アカウントの設定（script.google.com/home/usersettings）で Apps Script API をオンにしても、`projects.deployments.list` が 403 `SERVICE_DISABLED` を返した。スクリプトに紐づく既定の Cloud プロジェクトの側で Apps Script API が無効なため
  - エラーが示す有効化の画面を持ち主のアカウントで開くと、「追加のアクセス権が必要です」（`resourcemanager.projects.get` の権限がない）となり、有効にできなかった。既定の Cloud プロジェクトは持ち主でも開けない
- 設計への影響
  - 既定の Cloud プロジェクトのままでは、スクリプトが Apps Script API で自分の中身、スクリプトのバージョン、デプロイを変える方式は成り立たない
  - この方式を残すには、オーナーが標準の Cloud プロジェクトを作り、API の有効化、同意画面の設定、プロジェクト番号の付け替えを行う必要がある。初回の手順が重いので採らない
  - スクリプトの中身は最初のコピーのまま変えず、「システムを更新」はリリースのコードをスプレッドシートに保存するだけにし、実行のたびに保存したバンドルを読み込んで動かす方式（読み込み方式）を検証する（2026-11-21 決定）
  - Apps Script API を使う方式の確かめ（シナリオ 1〜4、6、8〜10）は行わない。シナリオ 5 と 6 は、読み込み方式 7（リリースの添付ファイルを取れる）と 8（Web アプリは持ち主の権限で動く）で確かめる。読み込み方式の確かめは `spikes/T1-1-loader/` で行う

### 読み込み方式の検証

検証コードと実行の手順は `spikes/T1-1-loader/` にある。上のシナリオ 7 の結果を受けて、保存したバンドルを実行のたびに読み込む方式を確かめる。検証には、検証用のコード A、B（中身を見分けられるようにした2つのコード。保存場所の A、B とは別）を使った。

#### 読み込み方式 1. 保存したバンドルを 5 つの入口から動かせる

- 確かめたこと
  - 保存したバンドルを、検証コードのメニュー、シンプルトリガー（onOpen）、Web アプリ（doGet）、画面の API（google.script.run）、時間主導のトリガーのそれぞれから読み込んで動かせるか（`spikes/T1-1-loader/README.md` の手順 1、2、4、5）
- 結果
  - 動いた（2026-11-22、個人の Gmail アカウントのテスト用スクリプト）。初期設定、検証コードのメニュー、onOpen、Web アプリ（doGet）、画面の API（google.script.run）、時間主導のトリガーのすべてで、保存したバンドルを `new Function` で評価して動かせた
  - onOpen（シンプルトリガー）の中でも、シート、スクリプトのプロパティ、キャッシュを読んで検証コードのメニューを作れた
- 設計への影響
  - 読み込み方式は GAS で成り立つ。ローダーは入口の関数だけを持ち、中身はすべて保存したバンドルに置ける

#### 読み込み方式 2. 読み込みの時間

- 確かめたこと
  - 読み込みの時間（シートから、キャッシュから）。本番に近い大きさで（`spikes/T1-1-loader/README.md` の手順 2、6、11）
- 結果
  - 約 16,000 字のバンドルで、シートから読むと 0.27〜0.57 秒（1回だけ 1.8 秒）、キャッシュから読むと 0.04〜0.12 秒。評価と JSON の解析はどちらも 1 ms 以下
  - 本番に近い大きさ（手順 11）は確かめていない
- 設計への影響
  - キャッシュがあれば、読み込みの時間は気にならない。キャッシュが切れた後の最初の1回は、1〜2 秒かかることがある
  - 本番のバンドルが大きくなった場合の時間は、フェーズ4 で確かめる

#### 読み込み方式 3. 「システムを更新」で切り替わり、1回押したときの処理の中で新しいコードを呼べる

- 確かめたこと
  - 「システムを更新」で、リリースから取ったバンドルに切り替わり、1回押したときの処理の中で新しいコードのメニューの公開を呼べるか（`spikes/T1-1-loader/README.md` の手順 6）
- 結果
  - リリースから取得、使っていない保存場所への保存、使用中の指定の切り替え、新しいコードでのメニューの公開までが、3 秒ほどで済んだ
  - 1回押したときの処理の中で、切り替えた後に読み込み直した検証用のコード B の `publishMenu` を呼べた（ログの「コード」の列が B）
- 設計への影響
  - 最初の方式で問題だった「置き換えの後に、新しいコードでメニューを公開し直す」は、1回押したときの処理の中で済む。トリガーやオーナーの押し直しは要らない

#### 読み込み方式 4. 切り替えの直後に Web アプリが新しいコードになる

- 確かめたこと
  - 切り替えた直後に Web アプリを再読み込みすると、新しい HTML とコードになるか。URL は変わらず、デプロイの作り直しは要らないか（`spikes/T1-1-loader/README.md` の手順 6）
- 結果
  - 「システムを更新」の後に Web アプリのタブを再読み込みするだけで、画面（コード B の HTML）とサーバーのコード（コード B）の両方が切り替わった。戻した後も、再読み込みで両方がコード A になった。URL は変わらず、デプロイの作り直しは要らなかった
  - コード B のときに読み込んだ画面のまま、戻した後に画面の API を呼ぶと、サーバーはコード A で答えた（画面は B、API は A の食い違い）
- 設計への影響
  - Web アプリのデプロイは初回に1つ作るだけでよい
  - 更新や戻しの前に開いた画面は、システムのバージョンが今のサーバーと合わないまま API を呼ぶ。画面は自分のシステムのバージョンを API に送り、サーバーのシステムのバージョンと違えば再読み込みを促す仕組みが要る

#### 読み込み方式 5. 途中で止めても続きから進み、二重に押しても 1 回だけ進む

- 確かめたこと
  - 各工程の後で止めても、もう一度押すと続きから進むか。二重に押しても 1 回しか進まないか（`spikes/T1-1-loader/README.md` の手順 8）
- 結果
  - 二重に押すと、2回目は「別の更新が動いている」として何もしなかった（LockService）
  - 各工程の後で止まることは確かめた（検証コードのメニューでは、工程を段階 1〜4 と呼んだ。1 は取得、2 は保存、3 は切り替え、4 はメニューの公開のやり直し）。切り替えの前（取得か保存の後）で止まったときは、使用中の指定は切り替わっておらず、今のコードはそのまま動いた。切り替えの後（切り替えか、メニューの公開のやり直しの後）で止まったときは、新しいコードに切り替わっていた
  - 止まった後にもう一度押して続きから進むかは、確かめていない
- 設計への影響
  - 続きから進める仕組み（どの工程まで済んだかの記録）は本番では持たず、止まったらもう一度押すと最初からやり直す形にする（2026-11-22 決定）。最初からやり直しても前のコードを失わない理由は次のとおり
    - 切り替えの前（取得か保存の後）で止まった場合は、使っていない保存場所に書いただけなので、今のコードも戻す先も変わらない
    - 切り替えの後（切り替えか、メニューの公開のやり直しの後）で止まった場合は、使用中の指定がもう新しい保存場所を指している。そのまま最初からやり直すと、前のコードの保存場所に同じ新しいコードを書いて戻す先を失う。このため取得の工程で、取ったバンドルが使用中の保存場所のバンドルと同じシステムのバージョンなら、保存と切り替えを飛ばす。その場合は、メニューの公開のやり直しだけを行う
  - 二重に押されるのを防ぐため、LockService は使う

#### 読み込み方式 6. 前のバージョンに戻せる

- 確かめたこと
  - 前のバージョンに戻すと、検証コードのメニューも Web アプリも前のコードに戻るか。更新が途中で止まった後でも戻せるか（`spikes/T1-1-loader/README.md` の手順 9）
- 結果
  - 「前のバージョンに戻す」で使用中の指定が前の保存場所に戻り、検証コードのメニューも Web アプリも前のコードになった。GitHub には触れない
  - 切り替えの後（切り替えか、メニューの公開のやり直しの後）で止まった後にも戻せた。切り替えの前（取得か保存の後）で止まったときは、戻す必要がない（使用中の指定が切り替わっていない）と返した
- 設計への影響
  - 戻す先は直前の1つだけ（保存場所が2つしかない）。それより前に戻すときは、デザイン担当が前のリリースを最新として出し直す

#### 読み込み方式 7. リリースの添付ファイルを取れる

- 確かめたこと
  - GitHub のリリースの添付ファイルを、`UrlFetchApp` で認証なしに取れるか（転送のたどり方）（`spikes/T1-1-loader/README.md` の手順 3）
- 結果
  - 認証なしで取れた。`releases/download/<タグ>/` は転送1回、`releases/latest/download/` は転送2回で、`UrlFetchApp` は既定で転送をたどった。本文は JSON として読めた
  - 添付ファイルを差し替えた直後の数十秒は、`latest` の URL から古い中身が返った
- 設計への影響
  - 取得先は `releases/latest/download/ouca-bundle.json` に固定できる
  - リリースを出した直後に「システムを更新」を押すと、古い中身を取る可能性がある。取ったバンドルの `version` をダイアログに出し、オーナーが確かめられるようにする

#### 読み込み方式 8. Web アプリは持ち主の権限で動く

- 確かめたこと
  - Web アプリは持ち主の権限で動くか（別のアカウントで開く。任意）（`spikes/T1-1-loader/README.md` の手順 10）
- 結果
  - Web アプリの `getEffectiveUser` は持ち主のアドレスだった（持ち主が自分で開いた場合）
  - 別のアカウントで開く確かめは行っていない
- 設計への影響
  - 「自分として実行」のデプロイを持ち主が作れば、持ち主の権限で動く。別のアカウントでの確かめは、T1-2（テンプレートのコピー）で別のアカウントを使うときに行う

#### 読み込み方式 9. マニフェストにない範囲を新しいコードが使ったときの動き

- 確かめたこと
  - マニフェストにない権限の範囲を、保存した新しいコードが使ったときの動き（承認を求められるか、エラーか）（`spikes/T1-1-loader/README.md` の手順 7）
- 結果
  - マニフェストにない範囲を使う関数（`MailApp.getRemainingDailyQuota`）を保存したバンドルから呼ぶと、承認を求められず、「指定された権限では呼び出すことができません」という例外になった
- 設計への影響
  - ローダーのマニフェストは後から変えられないので、将来使う可能性のある範囲（メールの送信など）も、テンプレートのマニフェストに最初から書いておく。新しい範囲が要る更新は、オーナーにエディタでの作業を頼むことになるので避ける

#### 読み込み方式 10. 初回の Web アプリのデプロイをエディタで作れる

- 確かめたこと
  - 初回の Web アプリのデプロイを、エディタで手で作れるか（オーナーの初回の手順になる）。押したボタンと選んだ設定と出た画面（`spikes/T1-1-loader/README.md` の手順 4）
- 結果
  - 手順 4 の設定（「デプロイ ▸ 新しいデプロイ」、種類「ウェブアプリ」、「次のユーザーとして実行: 自分」、「アクセスできるユーザー: 全員」）で作れた。実際に押したボタンと選んだ設定と画面の文言は記録していない
- 設計への影響
  - Apps Script API が使えないので、初回の Web アプリを作る操作は、オーナーがエディタで手で行う。オーナーの初回の手順に入れる（`delivery-flow.md` §4.1）。画面の文言との照合と、画面写真つきの手順は T6-3（オーナー向け手順書）で行う

## T1-2 テンプレートのコピー（Issue #8）

検証コードと実行の手順は `spikes/T1-2-template/` にある。見出しの番号は、Issue #8 の要件のシナリオの順番（見出しの文言は、Issue の題名より短くしたものがある）。テスト用スプレッドシートをテンプレートの代わりにした（持ち主はテンプレート側のアカウント。以降は「テンプレート側」と書く）。別の個人の Gmail のアカウント（コピー側のアカウント。以降は「コピー側」と書く）に閲覧者として共有し、コピー側が「コピーを作成」を押した（2026-11-22）。共有の設定「閲覧者と閲覧者（コメント可）にダウンロード、印刷、コピーの権限を付与する」はオンのままで、「コピーを作成」の画面のチェックボックスは、手順では変えないことにしていた（`spikes/T1-2-template/README.md` の手順 4）。

### 1. コピーすると、紐づいたスクリプトも複製される

- 確かめたこと
  - 閲覧者がコピーを作ったとき、コピー先にスクリプトが複製されるか
- 結果
  - 複製された。コピー先のエディタに検証コードのファイルがあり、コピー先でメニュー OUCA の処理が動いた。スクリプトの ID はテンプレートと違った
- 設計への影響
  - オーナーはテンプレートを閲覧できればコピーを作れる。テンプレートの編集者に招かなくてよい。閲覧者にコピーを許す共有の設定はオンにしておく

### 2. コピーしたスクリプトはコピーした人の持ち物になる

- 確かめたこと
  - スプレッドシートとスクリプトの持ち主。テンプレートの持ち主が、編集者、閲覧者、保護の編集者に残るか
- 結果
  - スプレッドシートの持ち主（`getOwner`）と、権限を使って動いている人（effective。`getEffectiveUser`）は、コピー側だった。Apps Script のホームの「マイプロジェクト」でも、このスクリプトの「オーナー」はコピー側（「自分」）と出た
  - 編集者、閲覧者、保護の編集者のどれにも、テンプレート側は残らなかった。保護の編集者はテンプレート側からコピー側に置き換わった
  - オーナーの操作の呼び出し元の確かめ（操作している人（active）、権限を使って動いている人（effective）、`getOwner()` の一致。`design.md` §3.3）は、コピー先で、コピー側のアカウントが操作すると通った
- 設計への影響
  - 「コピーを作成」の画面のチェックボックスを初期の状態のまま作ったコピーでは、テンプレートの持ち主（デザイン担当）とオーナーのシートのつながりは残らなかった。`delivery-flow.md` §1 の方針が成り立つ
  - 保護の編集者はコピーした人に置き換わるので、初期設定で保護の編集者を直す処理は要らない

### 3. コピー先でメニュー OUCA が出る

- 確かめたこと
  - コピーを初めて開いたとき、メニュー OUCA が出るか。出るまでに要る操作
- 結果
  - 承認の前でも開いた直後にメニュー OUCA が出たが、使用中の指定がコピーされないので（下の「追加の確認」）、メニュー OUCA は、項目が「初期設定」と「コピー先を調べる」だけの、初期設定の前の形だった
  - 承認の前のシンプルトリガー（onOpen）は、シートに書き込めた
  - 最初に押したメニュー OUCA の項目（コピー先を調べる）で、承認の画面が出た。承認の直後に押した処理が動いたかは記録していない（手順書どおり、承認の後に押し直した）。その後の初期設定では承認の画面が出ず、1回押すだけで動いた
  - 承認の画面の文言と権限の一覧は記録していない
- 設計への影響
  - オーナーの初回の手順（`delivery-flow.md` §4.1 の手順 3）は、最初に「OUCA ▸ 初期設定」を押して承認する今の形でよい
  - 初期設定の前は、ローダーが「初期設定」など少しの項目だけのメニュー OUCA を出す。手順書（T6-3 オーナー向け手順書）では、初期設定の前と後でメニュー OUCA の項目が変わることを書く

### 4. 保護、入力規則、条件付き書式、グラフ、ボタンの割り当てが残る

- 確かめたこと
  - テンプレートに作ったものが、コピー先に同じ形で残るか
- 結果
  - すべて残り、テンプレートと同じだった
    - 保護: シート全体 1 つ、範囲 2 つ。説明、範囲、警告のみの設定も同じ
    - 入力規則: リスト、別の範囲を参照するリスト、チェックボックス、数値の範囲の 4 種類
    - 条件付き書式 2 つ、縦棒グラフ（データの範囲も同じ）
    - 画像のボタンと、割り当てた関数の名前
  - コピー先で画像のボタンを押すと、割り当てた処理が動いた
- 設計への影響
  - テンプレートに作った保護、入力規則、書式、グラフ、ボタンは、コピー先で作り直さなくてよい（`design.md` §8 のとおり）

### 5. 非表示の _コード タブが残り、ローダー経由でメニュー OUCA が出る

- 確かめたこと
  - コピー先に `_コード` タブとその保護が残るか。初期設定と承認の後に、メニュー OUCA がローダー経由で出るか
- 結果
  - `_コード` は非表示のまま残った。保護と中身（文字数と、`_コード` タブの 1 行目に書いた、保存したバンドルの id）もテンプレートと同じだった
  - 初期設定の後に再読み込みすると、メニュー OUCA は `_コード` タブに保存したバンドルから出た
- 設計への影響
  - テンプレートに保存したバンドルはコピー先でそのまま使えるが、使用中の指定は作り直す必要がある（下の「追加の確認」）

### 6. コピーした人が作った Web アプリは、その人の権限で動く

- 確かめたこと
  - コピー側がエディタで Web アプリを作り（デプロイ）、別のブラウザで開いたとき、コピー側の権限で動くか
- 結果
  - 開けたブラウザ（コピー側のブラウザと、ログインしていないブラウザ）では、どちらもコピー側の権限で動いた
    - コピー側のブラウザ: `getEffectiveUser` はコピー側、`getActiveUser` もコピー側
    - ログインしていないブラウザ（シークレットウィンドウ）: `getEffectiveUser` はコピー側、`getActiveUser` は空
  - テンプレート側がふだん使うブラウザで開くと、Google ドライブの「Sorry, unable to open the file at this time.」の画面になり、開けなかった。原因は確かめていない。ブラウザに複数の Google アカウントでログインしていると起こる可能性がある。テンプレート側のブラウザに何個のアカウントでログインしていたかは記録していない
  - エディタで Web アプリを作る操作は、`delivery-flow.md` §4.1 の手順 4 の設定で行えた。押したボタンと選んだ設定と画面の文言は記録していない
- 設計への影響
  - オーナーが自分で作れば、Web アプリはオーナーの権限で動く。ログインしていないブラウザでも、オーナーの権限で動いた
  - ログインした別のアカウントで開く確かめ（読み込み方式 8「Web アプリは持ち主の権限で動く」で残したこと）は、テンプレート側のブラウザで開けなかったので済んでいない。T1-4（Web アプリの動作）に送る
  - Google アカウントにログインしたブラウザでは、開けない場合がある。お客さんのスマホ（LINE の中のブラウザ、Safari、Chrome）で開けるかは、T1-4 で確かめる。開けない場合に案内を出すかも、T1-4 で決める

### 7. コピー先にトリガーはコピーされない

- 確かめたこと
  - テンプレートのトリガーが、コピー先にコピーされるか
- 結果
  - コピーされなかった。テンプレートの 2 個に対し、コピー先は 0 個だった
  - コピー先で初期設定を押すと、時間主導のトリガーが 1 個できた。エディタの「トリガー」に、「オーナー」は「自分」で出た
- 設計への影響
  - 初期設定でトリガーを作る今の設計（`design.md` §8）のままでよい

### 追加の確認. スクリプトのプロパティはコピーされない

- 確かめたこと
  - 読み込み方式では、使用中の指定をスクリプトのプロパティに置いている（`design.md` §2.13）。プロパティがコピーされるか
- 結果
  - コピーされなかった。コピー先のスクリプトのプロパティには、値が 1 つもなかった
  - 初期設定の前のコピー先では、ローダーが保存したバンドルを読めず、初期設定の前のメニュー OUCA（「初期設定」など少しの項目だけ）を出した
  - 初期設定が、コピーされた `_コード` タブの、保存したバンドルの id から使用中の指定を作り直すと、保存したバンドルで動いた
- 設計への影響
  - テンプレートのコピーで初期設定が行うことに、使用中の指定を作り直すことを足す（2026-11-22 決定。`delivery-flow.md` §4.1、`design.md` §8）
  - 本番の `_コード` タブには保存場所が 2 つある。テンプレートで「前のバージョンに戻す」を押した後などは、新しい方の保存場所が使用中とは限らない
  - 使用中の指定を切り替えるときは、同じ内容を `_コード` タブのセルにも書く。シートはコピーされるので、コピー先の初期設定はこのセルの記録で使用中の保存場所を決める。セルの記録が使えないときの決め方は `design.md` §8 にある（2026-11-22 決定）
  - もう片方の保存場所は戻す先として扱わないので、コピーの直後は戻す先がない。2 つの保存場所での動きは、T4-1（シートの読み書きと初期設定）と T4-7（システムを更新、前のバージョンに戻す）で確かめる

### 確かめていないこと

- 「コピーを作成」、承認、デプロイの画面の文言は記録していない。オーナー向けの手順書（T6-3）で、画面写真と合わせて確かめる
- 「コピーを作成」の画面のチェックボックス（同じユーザーと共有するなど）の初期の状態と、チェックを付けたときの共有。チェックを付けると、テンプレートの共有相手がコピーの共有に入る可能性がある。T6-2（テンプレートのスプレッドシート）で確かめ、T6-3 の手順書に書く
- ログインした別のアカウントで Web アプリを開けるか（シナリオ 6「コピーした人が作った Web アプリは、その人の権限で動く」）。T1-4（Web アプリの動作）で確かめる
- テンプレートの共有のしかた。本番では「コピーを作成」のリンクを LINE で送るので、一般的なアクセスが「リンクを知っている全員（閲覧者）」になる可能性がある。この検証は、テスト用スプレッドシートを広く共有しないように、「制限付き」でコピー側を閲覧者に追加して行った。共有のしかたは T6-2 で決める

## T1-3 シートの機能（Issue #9）

検証コード、設計（シナリオごとの判定の表）、手順は `spikes/T1-3-sheet-features/` にある。2026-11-28、個人の Gmail アカウントのテスト用スプレッドシートで、PC の Chrome、iPhone のスプレッドシートアプリと Safari、別のアカウント（B）、ログインしていないブラウザで確かめた。結果はログの事実から判定を計算する「まとめ」と、ユーザーの控えで決めた。見出しの番号は `DESIGN.md` のシナリオの番号（S01〜S18）。

### S01 複数選択のプルダウンを Apps Script から設定できる

- 確かめたこと
  - 入力規則のビルダーで複数選択を設定できるか。手でオンにした設定が、高度な Sheets サービスの JSON に出るか。セルのコピー（`PASTE_DATA_VALIDATION`）と、`getDataValidation().copy().build()` での作り直しで残るか
- 結果
  - ビルダーには複数選択に当たるメソッドがなかった（35 個のメソッドを調べた）。Apps Script で設定した直後のセルでは、複数選べなかった
  - 入力規則の画面で、表示形式を「チップ」にして「複数選択を許可」をオンにすると、複数選べた
  - オンにする前と後で、高度な Sheets サービスで読んだ入力規則の JSON に違いはなかった（複数選択は JSON に出ない）
  - 高度な Sheets サービスで、手でオンにしたセルの JSON を別のセル（D4）に書き込むと、読み戻した D4 の JSON は空だった（入力規則が付かなかった）
  - 手でオンにしたセルをコピーしたセルでも、`getDataValidation().copy().build()` で作り直して設定したセルでも、複数選べた
  - 複数選んだセルの値は「ナッツ, 果実」のように、カンマと空白で区切った1つの文字列になった（`getValue` と `getDisplayValue` が同じ）
- 設計への影響
  - スクリプトは、複数選択のプルダウンを一から作れない。テンプレートに手でオンにした見本のセルを置き、「項目を追加」がそこからコピーして設定する
  - 「メニューを公開」が入力規則を整えるときは、既にある入力規則を `copy()` から作り直す。一から作り直さない（一から作ると複数選択が消える見込み。`copy()` の後に範囲を変えて残るかは、T4-5（項目を追加）で確かめる）
  - 複数の値は「, 」で区切って読む

### S02、S03、S09 メニュー、時間主導、インストール型の編集トリガーから末尾 `_` の関数を呼べる

- 確かめたこと
  - `addItem`、`ScriptApp.newTrigger(...).timeBased().after()`、`ScriptApp.newTrigger(...).forSpreadsheet().onEdit()` に、末尾 `_` の関数を指定して動くか
- 結果
  - どれも動いた。トリガーも作れた
- 設計への影響
  - メニューにだけある操作と、インストール型のトリガーの入口は、末尾 `_` の名前にできる。画面（`google.script.run`）から呼べない入口になる

### S04 候補を足すと、数式を参照するプルダウンに自動で出る

- 確かめたこと
  - `_リスト` の数式（VSTACK）の元の項目タブに候補を足したとき、`_リスト` と、それを参照するプルダウンの範囲に入るか
- 結果

### S15〜S18 管理用の Web ページ

- 確かめたこと
  - 持ち主が Web アプリから呼ぶと持ち主の確かめが通るか（S15）。アクセスを「自分のみ」にした2つ目のデプロイを作れ、ほかの人が開けないか（S16）。doGet が、どちらのデプロイから開かれたかを見分けられるか（S17）。持ち主のスマホのブラウザで2つ目のデプロイを開けるか（S18）
- 結果
  - 持ち主（A）がログインしたブラウザで開いて `google.script.run` から呼ぶと、持ち主の確かめが通った（S15）
  - 同じスクリプトに、アクセスを「自分のみ」にした2つ目のデプロイを作れた。アカウント B のブラウザとログインしていないブラウザでは開けなかった（S16）
  - デプロイの画面で選んだアクセスは、そのとき作るスクリプトのバージョンと、HEAD のマニフェストに入った。1つ目（全員）のデプロイのバージョンのマニフェストは変わらなかった（Issue #9 のコメント）
  - doGet の中の `ScriptApp.getService().getUrl()` は、開いたデプロイごとに違う値を返した（URL の引数 `d` でも見分けられる）。`e` の鍵（`contentLength`、`contextPath`、`parameter`、`parameters`、`queryString`）と、URL の引数に由来しない値は、2つのデプロイで同じだった（S17）
  - 持ち主のスマホの Safari で2つ目のデプロイを開き、持ち主の確かめが通った（S18）
- 設計への影響
  - 持ち主だけが使える管理画面（Web ページ）を、同じスクリプトで出せる。doGet は、`getUrl()` でも URL の引数でも、お客さんの画面と管理画面を出し分けられる。出し分けの方法と、2つ目のデプロイを使うかは #54 で決める。守りは、デプロイのアクセスの設定ではなく、持ち主の確かめで行う
  - 2つ目のデプロイを作ると HEAD のマニフェストのアクセスが「自分のみ」になるので、その後にお客さんのデプロイを新しいバージョンで出し直すと、お客さんが開けなくなる可能性がある（確かめていない）。読み込み方式ではデプロイを出し直さないので、ふだんは起きない。管理画面を2つ目のデプロイで出す場合は、手順書に「お客さんのデプロイは出し直さない」と書く
  - ユーザーの判断で、管理は Web ページの管理画面で行う方向にした（Issue #9、#50）

### 操作の中で分かったこと

- 同じブラウザにアカウント B（既定）と A（持ち主）でログインしていると、1つ目（全員）のデプロイも、アドレスが `/macros/u/1/s/…` になって「現在、ファイルを開くことができません。」で開けなかった。B だけでログインしたブラウザでは開けた。T1-4（Web アプリの動作）で、開き方ごとに確かめる（Issue #10 のコメント）
- 2つのインストール型の編集トリガーが同じ編集で動いた所で、ログのタブに、日時の列が数値になった行と、空の行が1つずつできた。2つが同時に書いたことが原因の可能性がある。同時に書き得る処理は `LockService` で順番にする
- GAS は、送るときの構文の確かめで、文字列の中にそのまま書いた U+2028、U+2029 を受け付けなかった（T1-4 の検証コードを送ったときに分かった。T1-4 の節にも書いた）。エスケープで書く

### 確かめていないこと

- 持ち主のスマホのブラウザで、1つ目（全員）のデプロイから持ち主の確かめが通るか（S18 で確かめたのは2つ目だけ）。管理画面の出し方を決める #54 で確かめる
- 複数のアカウントでログインしたブラウザで、管理画面を開けるか（T1-4）
- `copy()` の後に範囲を変えても、複数選択が残るか（T4-5（項目を追加））
- 2つ目のデプロイを作った後に、お客さんのデプロイを新しいバージョンで出し直したときに、アクセスがどうなるか
- 管理タブのチェックボックスをスマホのスプレッドシートアプリで付けたときの、持ち主の確かめの結果（S10 のログには編集トリガーの行として含まれる可能性があるが、スマホからの行と分けて確かめていない）

### W7 往復の時間

- 確かめたこと
  - `google.script.run` で、5KB、50KB、200KB の JSON の文字列を返す往復の時間（各5回）
- 結果
  - PC の Chrome（A）: 中央値は 5KB が 883 ミリ秒（最大 1019）、50KB が 699 ミリ秒（最大 711）、200KB が 623 ミリ秒（最大 828）
  - PC の Chrome（B）: 5KB の中央値 730 ミリ秒
  - iPhone の LINE の中のブラウザ: 5KB の中央値 616 ミリ秒。50KB と 200KB の行は来なかった。往復の処理は大きさごとに5回測ってから行を送るので、50KB の途中で画面を離れたか、失敗した可能性があるが、理由は分からない。回線（Wi-Fi かモバイルか）は控えていない
  - まとめの判定は未確定だった。まとめを作ったのが LINE の行が来る前だったため（LINE の行の開き方とビルドの印は、ほかの行と同じだった）。LINE の行を含めると、判定の表の「往復も実用の速さ」に当たる
  - PC では大きさによる差が小さく、1回の往復に 0.6〜0.9 秒かかった。LINE でも同じと見込む（50KB と 200KB は確かめていない）
- 設計への影響
  - 埋め込み（§4.2）を使い続ける。管理画面（#54）は操作ごとに往復するので、1回の往復に 0.6〜0.9 秒かかる前提で、保存中の表示と、まとめて送る作りにする

- 設計への影響
  - iPhone の Safari と LINE の中のブラウザでは、ログインしているアカウントの控えがない。ホーム画面のアイコンからは A（持ち主）だった。Safari が A でログインしていた場合、Safari の「開けた」はお客さんの状況を表さない
  - まとめの判定は未確定だった（手順 5 と 12 を飛ばしたため）。判定の表どおりなら、「B が既定で A も追加」が開けなかったので「案内が要る」に当たり、影響は「オーナーが LINE で送る文と手順書に書く」になる
  - 開けなかったのは、持ち主のアカウントが入ったブラウザだけで、お客さんのブラウザに持ち主のアカウントが入っていることはふつうない。そのため、お客さんに LINE で送る文には書かず、オーナー向けの手順書の「困ったとき」に「開けないときは、シークレットウィンドウか別のブラウザで開く」と1行書く（T6-3）。ただし、T1-2 で開けなかったブラウザに持ち主のアカウントが入っていたかは記録がなく、持ち主を含まない複数ログインでも開けない可能性は残る（下の「確かめていないこと」）
  - オーナーが管理画面を開くブラウザは、持ち主のアカウントだけでログインしたものにする（#54 の問い「オーナーがいくつのアカウントでログインしているか」に関わる）

### 操作の中で分かったこと

- GAS は、送るときの構文の確かめで、文字列の中にそのまま書いた U+2028、U+2029 を受け付けず、「Unexpected token ILLEGAL」で送れなかった。エスケープ（` `）で書く。`spikes/T1-4-webapp/test/wiring.test.ts` で、送るファイルにそのまま書いていないことを確かめる
- メモ帳に「exec:」の見出しを付けた行ごとアドレス欄に貼ると、Chrome は URL として開かず、Google の検索にかけた。手順書では、見出しを URL と別の行に書く

### 確かめていないこと

- Android の Chrome と LINE の中のブラウザ
- ログインしていないブラウザ（T1-3 でログインしていないブラウザから開けることは確かめた）
- 自分のアカウントを複数持つお客さんのブラウザ（持ち主のアカウントを含まない複数ログイン）。T1-2 で開けなかったふだんのブラウザに、コピー側（デプロイした持ち主）のアカウントが入っていたかの記録がない
- iPhone の Safari の開き直し、PC でブラウザを閉じてからの開き直し
- LINE の URL の引数 `openExternalBrowser=1` で外のブラウザに開けるか（T5-3）
- iOS で7日ほど開かないと保存が消える仕組み（ITP）
