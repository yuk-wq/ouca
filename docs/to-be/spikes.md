### 7. 既定の Cloud プロジェクトのままで Apps Script API を呼べる

- 確かめたこと
  - `UrlFetchApp` と `ScriptApp.getOAuthToken()` で Apps Script API を呼べるか。呼べない場合に、Cloud プロジェクトの作成をオーナーに頼む必要があるか
- 結果
  - 呼べなかった（2026-11-21、個人の Gmail アカウントのテスト用スクリプト）
  - アカウントの設定（script.google.com/home/usersettings）で Apps Script API をオンにしても、`projects.deployments.list` が 403 `SERVICE_DISABLED` を返した。スクリプトに紐づく既定の Cloud プロジェクトの側で Apps Script API が無効なため
  - エラーが示す有効化の画面を持ち主のアカウントで開くと、「追加のアクセス権が必要です」（`resourcemanager.projects.get` の権限がない）となり、有効にできなかった。既定の Cloud プロジェクトは持ち主でも開けない
- 設計への影響
  - 既定の Cloud プロジェクトのままでは、スクリプトが Apps Script API で自分の中身、バージョン、デプロイを変える方式は成り立たない
  - この方式を残すには、オーナーが標準の Cloud プロジェクトを作り、API の有効化、同意画面の設定、プロジェクト番号の付け替えを行う必要がある。初回の手順が重いので採らない
  - 代わりに、スクリプトの中身は最初のコピーのまま変えず、「アプリを更新」はリリースのコードをスプレッドシートに保存するだけにし、実行のたびに保存したコードを読み込んで動かす方式（読み込み方式）を検証する（2026-11-21 決定）
  - Apps Script API を使う方式の確かめ（シナリオ 1〜4、6、8〜10）は行わない。シナリオ 5 と 6 は、読み込み方式 7 と 8 で確かめる。読み込み方式の確かめは `spikes/T1-1-loader/` で行う

### 読み込み方式の検証

検証コードと実行の手順は `spikes/T1-1-loader/` にある。上のシナリオ 7 の結果を受けて、保存したコードを実行のたびに読み込む方式を確かめる。

#### 読み込み方式 1. 保存したコードを 5 つの入口から動かせる

- 確かめたこと
  - 保存したコードを、メニュー、シンプルトリガー（onOpen）、Web アプリ（doGet）、画面の API（google.script.run）、時間主導のトリガーのそれぞれから読み込んで動かせるか（手順 1、2、4、5）
- 結果
  - 動いた（2026-11-22、個人の Gmail アカウントのテスト用スクリプト）。初期設定、メニュー、onOpen、Web アプリ（doGet）、画面の API（google.script.run）、時間主導のトリガーのすべてで、保存したコードを `new Function` で評価して動かせた
  - onOpen（シンプルトリガー）の中でも、シート、スクリプトのプロパティ、キャッシュを読んでメニューを作れた
- 設計への影響
  - 読み込み方式は GAS で成り立つ。ローダーは入口の関数だけを持ち、中身はすべて保存したコードに置ける

#### 読み込み方式 2. 読み込みの時間

- 確かめたこと
  - 読み込みの時間（シートから、キャッシュから）。本番に近い大きさで（手順 2、6、11）
- 結果
  - 約 16,000 字のバンドルで、シートから読むと 0.27〜0.57 秒（1回だけ 1.8 秒）、キャッシュから読むと 0.04〜0.12 秒。評価と JSON の解析はどちらも 1 ms 以下
  - 本番に近い大きさ（手順 11）は確かめていない
- 設計への影響
  - キャッシュがあれば、読み込みの時間は気にならない。キャッシュが切れた後の最初の1回は、1〜2 秒かかることがある
  - 本番のバンドルが大きくなった場合の時間は、フェーズ4 で確かめる

#### 読み込み方式 3. 「アプリを更新」で切り替わり、同じ実行で新しいコードを呼べる

- 確かめたこと
  - 「アプリを更新」で、リリースから取ったコードに切り替わり、同じ実行の中で新しいコードのメニューの公開を呼べるか（手順 6）
- 結果
  - リリースから取得、使っていない枠への保存、印の切り替え、新しいコードでのメニューの公開までが、3 秒ほどで済んだ
  - 同じ実行の中で、切り替えた後に読み込み直したコード B の `publishMenu` を呼べた（ログの「コード」の列が B）
- 設計への影響
  - 最初の方式で問題だった「置き換えの後に、新しいコードでメニューを公開し直す」は、同じ実行で済む。トリガーやオーナーの押し直しは要らない

#### 読み込み方式 4. 切り替えの直後に Web アプリが新しいコードになる

- 確かめたこと
  - 切り替えた直後に Web アプリを再読み込みすると、新しい HTML とコードになるか。URL は変わらず、デプロイの作り直しは要らないか（手順 6）
- 結果
  - 「アプリを更新」の後に Web アプリのタブを再読み込みするだけで、画面（HTML コード B）とサーバーのコード（コード B）の両方が切り替わった。戻した後も、再読み込みで両方がコード A になった。URL は変わらず、デプロイの作り直しは要らなかった
  - コード B のときに読み込んだ画面のまま、戻した後に画面の API を呼ぶと、サーバーはコード A で答えた（画面は B、API は A の食い違い）
- 設計への影響
  - Web アプリのデプロイは初回に1つ作るだけでよい
  - 更新や戻しの前に開いた画面は、今のサーバーとバージョンが合わないまま API を呼ぶ。画面は自分のバージョンを API に送り、サーバーのバージョンと違えば再読み込みを促す仕組みが要る

#### 読み込み方式 5. 途中で止めても続きから進み、二重に押しても 1 回だけ進む

- 確かめたこと
  - 各段階の後で止めても、もう一度押すと続きから進むか。二重に押しても 1 回しか進まないか（手順 8）
- 結果
  - 二重に押すと、2回目は「別の更新が動いている」として何もしなかった（LockService）
  - 各段階の後で止まることは確かめた。段階 1、2 の後で止まったときは、印は切り替わっておらず、今のコードはそのまま動いた。段階 3、4 の後で止まったときは、新しいコードに切り替わっていた
  - 止まった後にもう一度押して続きから進むかは、確かめていない
- 設計への影響
  - 続きから進める仕組み（段階の記録）は本番では持たず、止まったらもう一度押すと最初からやり直す形にする（2026-11-22 決定）。最初からやり直しても前のコードを失わない理由は次のとおり
    - 段階 1、2 の後で止まった場合は、使っていない枠に書いただけなので、今のコードも戻す先も変わらない
    - 段階 3、4 の後で止まった場合は、印がもう新しい枠を指している。そのまま最初からやり直すと、前のコードの枠に同じ新しいコードを書いて戻す先を失う。このため段階 1 で、取ったバンドルのバージョンが今の枠と同じなら、保存と切り替えを飛ばして段階 4 だけを行う
  - 二重に押されるのを防ぐため、LockService は使う

#### 読み込み方式 6. 前のバージョンに戻せる

- 確かめたこと
  - 前のバージョンに戻すと、メニューも Web アプリも前のコードに戻るか。更新が途中で止まった後でも戻せるか（手順 9）
- 結果
  - 「前のバージョンに戻す」で印が前の枠に戻り、メニューも Web アプリも前のコードになった。GitHub には触れない
  - 段階 3、4 の後で止まった後にも戻せた。段階 1、2 の後で止まったときは、戻す必要がない（印が切り替わっていない）と返した
- 設計への影響
  - 戻す先は直前の1つだけ（枠が2つのため）。それより前に戻すときは、デザイン担当が前のリリースを最新として出し直す

#### 読み込み方式 7. リリースの添付ファイルを取れる

- 確かめたこと
  - GitHub のリリースの添付ファイルを、`UrlFetchApp` で認証なしに取れるか（転送のたどり方）（手順 3）
- 結果
  - 認証なしで取れた。`releases/download/<タグ>/` は転送1回、`releases/latest/download/` は転送2回で、`UrlFetchApp` は既定で転送をたどった。本文は JSON として読めた
  - 添付ファイルを差し替えた直後の数十秒は、`latest` の URL から古い中身が返った
- 設計への影響
  - 取得先は `releases/latest/download/ouca-bundle.json` に固定できる
  - リリースを出した直後に「アプリを更新」を押すと、古い中身を取る可能性がある。取ったバンドルの `version` をダイアログに出し、オーナーが確かめられるようにする

#### 読み込み方式 8. Web アプリは持ち主の権限で動く

- 確かめたこと
  - Web アプリは持ち主の権限で動くか（別のアカウントで開く。任意）（手順 10）
- 結果
  - Web アプリの `getEffectiveUser` は持ち主のアドレスだった（持ち主が自分で開いた場合）
  - 別のアカウントで開く確かめは行っていない
- 設計への影響
  - 「自分として実行」のデプロイを持ち主が作れば、持ち主の権限で動く。別のアカウントでの確かめは、T1-2 で別のアカウントを使うときに行う

#### 読み込み方式 9. マニフェストにない範囲を新しいコードが使ったときの動き

- 確かめたこと
  - マニフェストにない権限の範囲を、保存した新しいコードが使ったときの動き（承認を求められるか、エラーか）（手順 7）
- 結果
  - マニフェストにない範囲を使う関数（`MailApp.getRemainingDailyQuota`）を保存したコードから呼ぶと、承認を求められず、「指定された権限では呼び出すことができません」という例外になった
- 設計への影響
  - ローダーのマニフェストは後から変えられないので、将来使う可能性のある範囲（メールの送信など）も、テンプレートのマニフェストに最初から書いておく。新しい範囲が要る更新は、オーナーにエディタでの作業を頼むことになるので避ける

#### 読み込み方式 10. 初回の Web アプリのデプロイをエディタで作れる

- 確かめたこと
  - 初回の Web アプリのデプロイを、エディタで手で作れるか（オーナーの初回の手順になる）。押した項目と出た画面（手順 4）
- 結果
  - README の手順 4 の設定（「デプロイ ▸ 新しいデプロイ」、種類「ウェブアプリ」、「次のユーザーとして実行: 自分」、「アクセスできるユーザー: 全員」）で作れた。実際に押した項目と画面の文言は記録していない
- 設計への影響
  - Apps Script API が使えないので、初回の Web アプリの公開は、オーナーがエディタで手で行う。オーナーの初回の手順に入れる（`delivery-flow.md` §4.1）。画面の文言との照合と、画面写真つきの手順は T6-3 で行う
