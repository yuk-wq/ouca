# T1-1 アプリの自己更新の検証

Issue #7。オーナーが「アプリを更新」を1回押すだけで最新のバージョンを取り込める設計が、GAS で成り立つかを確かめる。検証コードはテスト用スクリプトにだけ送る。本体（`src/`）には入れない。

## 用語

- 「バージョン」は、Apps Script が振るスクリプトのバージョン番号（整数）を指す
- 「コード A」は、いま送ってあるコード。「コード B」は、置き換え先の新しい中身。2つの違いは `SPIKE_CODE_LABEL` の1行だけで、どちらのコードで動いたかがメニュー名、ログ、Web アプリに出る

## 前提

- U-1 で作ったテスト用スプレッドシートと、`.clasp.test.json`（`scriptId` を書き換え済み）がある
- script.google.com/home/usersettings で「Google Apps Script API」をオンにしてある。シナリオ「既定の Cloud プロジェクトのまま」を確かめるため、スクリプトの Cloud プロジェクトは変えない
- `gh` コマンドで `yuk-wq/ouca` に書き込める
- リポジトリが公開になっている（受け入れ基準の D-5。公開前は、取得の確認が 404 になる）

## 権限の範囲（oauthScopes）を決めた理由

使う API から決めた。`gas/appsscript.json` にだけ書く。

| 範囲 | 使う場所 |
|---|---|
| `spreadsheets` | ログのタブと公開データのタブへの書き込み |
| `script.container.ui` | メニューの追加（`onOpen`） |
| `script.external_request` | `UrlFetchApp`（GitHub と Apps Script API） |
| `script.projects` | `projects.updateContent`、`projects.getContent`、`projects.versions.create`、`projects.versions.list` |
| `script.deployments` | `projects.deployments.list`、`create`、`update` |
| `script.scriptapp` | 1回だけの時間主導のトリガーの作成と削除。`ScriptApp.getOAuthToken()` |
| `userinfo.email` | `Session.getEffectiveUser().getEmail()`、`getActiveUser().getEmail()` |

過不足は検証で分かる。足りない範囲があると、API が 403 を返し、本文がログに出る。

## コード B のバンドルを作って公開する

```sh
node spikes/T1-1-self-update/make-bundle.mjs B
gh release create spike-t1-1 spikes/T1-1-self-update/out/ouca-bundle.json \
  --repo yuk-wq/ouca --title "T1-1 検証用" --notes "T1-1 の検証用。終わったら消す" --latest
```

- `--latest` を付けるのは、`releases/latest/download/` の URL も確かめるため。既に最新のリリースがある場合は、検証のあいだ最新が spike-t1-1 に変わる点に注意する
- 公開した後、ブラウザで `https://github.com/yuk-wq/ouca/releases/download/spike-t1-1/ouca-bundle.json` を開き、JSON が出ることを確かめる

## 送り方と初回の承認

1. リポジトリのルートで、コード A をテスト用スクリプトに送る

   ```sh
   npm run push:spike -- T1-1-self-update
   ```

   `.clasp.test.json` がないときは、作り方を表示して止まる。中身とマニフェストは丸ごと置き換わる

2. テスト用スプレッドシートを開き直す（ページを再読み込みする）。メニューバーに「T1-1 検証（コード A）」が出る
3. 「T1-1 検証」から「状態を見る」を押す。初回は承認を求められる
   - 「承認が必要です」で「続行」を押し、使うアカウントを選ぶ
   - 「このアプリは Google で確認されていません」で「詳細」を押し、「（プロジェクト名）（安全ではないページ）に移動」を押す
   - 要求された権限の一覧を確かめて「許可」を押す
4. もう一度「状態を見る」を押す。「T1-1 検証ログ」タブに行が出る

ログは「T1-1 検証ログ」タブに、日時、操作、コード、結果、詳細の列で追記される。結果は OK、NG、停止（意図）のどれか。NG の詳細には Apps Script API の応答の本文がそのまま入る。

## 検証の流れ

最初に1回だけ「初期の Web アプリを作る」を押す。これで、コード A のバージョン（1 になる）と、そのバージョンに向いた Web アプリのデプロイができる。以降は次の繰り返しになる。

1. 更新を試す（止める設定を選んでから「アプリを更新」を押す）
2. 結果をログと Web アプリで見る
3. 「前のバージョンに戻す」を押してコード A に戻す
4. 「記録を消す」を押し、次の検証へ

手順 3 のあとも、シートのメニュー名はスプレッドシートを開き直すまで古いままのことがある。

## シナリオとメニューとログの対応

| # | シナリオ | 押すメニュー | 見る場所と読み方 |
|---|---|---|---|
| 1 | 自分の中身を置き換えられる | 「アプリを更新（段階 1〜4）」 | ログ「更新 段階 2」が OK なら成功。NG なら本文（API が無効、権限不足など）が答え。使えた範囲は、マニフェストのとおり |
| 2 | バージョンとデプロイを作れる | 同上 | ログ「更新 段階 3」にバージョン番号。「更新 段階 4」に、update か create か、切り替え前後の URL、同じかどうか |
| 3 | 実行中に置き換えても最後まで動く | 同上 | 段階 2 の後の段階 3、段階 4 が OK なら動いた。それぞれの行の「コード」の列は、実行中のコードの区別（A のままなら、その実行は古いコードで動き続けている） |
| 4 | 置き換えの後に新しい「メニューを公開」を呼べる | 「アプリを更新（段階 1〜5）」、のち「メニューの公開の代わり（押し直し）」 | 「T1-1 公開データ」タブ。3 行できる（同じ実行から、1 分後のトリガー、押し直し）。各行の「動いたコード」が B なら新しいコード。同じ実行の行が A、トリガーの行が B なら、別の実行が要る |
| 5 | リリースの添付ファイルを取れる | 「取得を試す（固定の URL 2 つ）」 | ログ「取得を試す」。各 URL で、手動で 1 回ずつたどったときのコードと転送先のホスト、既定のまま取ったときの最終コードとバージョンが出る。リダイレクトの有無、既定でたどれたかが分かる |
| 6 | 持ち主として作ったものは「持ち主として実行」 | 「初期の Web アプリを作る」または「アプリを更新」で作ったデプロイを、ブラウザで開く | 下の「Web アプリを開く」を参照 |
| 7 | 既定の Cloud プロジェクトのままで API を呼べる | 「状態を見る」（最初の1回） | 最初に出るログが OK なら呼べた。NG で 403 なら、本文に出る理由（API が無効、Cloud プロジェクトの設定など）を、そのまま写す |
| 8 | 置き換えの直後、メニューは新しく、Web アプリは古いまま | 「止める設定 ▸ 段階 2 の後で止める」を選び、「アプリを更新（段階 1〜4）」 | 止まった後、(a) 「状態を見る」の「HEAD のコード」が B か、(b) スプレッドシートを開き直して「メニューの公開の代わり（押し直し）」を押し、「T1-1 公開データ」の動いたコードが B か、(c) Web アプリを開いて A のままか |
| 9 | 各段階の後で止めても続きから進める | 「止める設定 ▸ 段階 N の後で止める」を選んでから「アプリを更新」を押し、止まったらもう一度「アプリを更新」を押す。N は 1 から 4 までを順に | 1 回目のログが「停止（意図）」になる。2 回目のログに「段階 N は済み。飛ばす」と最後までの段階が出る。止める設定は1回止めると消える |
| 10 | 前のバージョンの中身を番号から取り出せる | 「前のバージョンに戻す」 | ログ「前のバージョンに戻す」。取り出せたバージョン番号とコードの区別（A のはず）、HEAD に戻したか、デプロイの向け先。段階 2 または 3 の後で止めたあとにも押して、同じ番号で取り出せるかを見る |

## 手順の詳細

### 準備の確認（シナリオ 7 を含む）

1. 「状態を見る」を押す。「T1-1 検証ログ」の最初の行が API の呼び出しの結果になる
2. 「初期の Web アプリを作る」を押す。ログにバージョン番号と URL が出る。この URL を控える

### シナリオ 5

1. 「取得を試す（固定の URL 2 つ）」を押す
2. 検証の前に、手元で作ったバンドルをリリースに載せてあること（上の「コード B のバンドルを作って公開する」）

### シナリオ 1、2、3、4、8、9、10 をまとめて確かめる順番

1. 「止める設定 ▸ 段階 2 の後で止める」を押す
2. 「アプリを更新（段階 1〜5）」を押す。段階 2 の後で停止してエラーのダイアログが出る（意図した停止）。これがシナリオ 8 の「置き換えの直後」の状態になる
3. この状態で、次を見る
   - 「状態を見る」を押し、HEAD のコードが B、デプロイの向け先のバージョンが 1 のままであること
   - 手順 2 のあとスプレッドシートを開き直す。メニュー名が「コード B」になっていること
   - 「メニューの公開の代わり（押し直し）」を押し、公開データの動いたコードが B であること
   - 初期の Web アプリの URL を開き、「コード A」と出ること（デプロイは古いバージョンのまま）
4. 「前のバージョンに戻す」を押す（シナリオ 10 の、止まった後でも同じ番号で取り出せるかの確認になる。ログの結果で判断する）
5. 「記録を消す」を押す
6. 止める設定なしで「アプリを更新（段階 1〜5）」を押す。段階 1〜5 が OK で終わる（シナリオ 1、2、3）。1 分ほど待ち、「T1-1 公開データ」に、同じ実行、1 分後のトリガーの行が付くのを確かめる（シナリオ 4）。「メニューの公開の代わり（押し直し）」を押して3つ目の行を作る
7. Web アプリの URL を開き、「コード B」と出ること。URL は初期の Web アプリと同じ（シナリオ 2）
8. 「前のバージョンに戻す」を押し、「記録を消す」を押す。コード A に戻る

### 段階の止め方（シナリオ 9）

1. 「止める設定 ▸ 段階 1 の後で止める」を選び、「アプリを更新（段階 1〜4）」を押す。段階 1 が OK のあと「停止（意図）」になる
2. 止める設定が消えているので、そのまま「アプリを更新（段階 1〜4）」を押す。「段階 1 は済み。飛ばす」のあと、段階 2 から 4 が進む
3. 「前のバージョンに戻す」、「記録を消す」でコード A に戻す
4. 段階 2、3、4 についても同じことを繰り返す。段階 3 の後で止めるときは、ログのバージョン番号が、もう一度押した後にも変わらず使われることを見る。段階 4 の後で止めるときは、段階 5 を付けずに押す

### 取得先を latest に切り替える

「取得先を切り替える（spike / latest）」を押すと、取得先が `releases/latest/download/` の URL に変わる。もう一度押すと戻る。「アプリを更新」は、「記録を消す」の後の最初の押下で、そのときの取得先を使う。

### Web アプリを開く（シナリオ 6）

1. 「状態を見る」のログに出る Web アプリの URL（`https://script.google.com/macros/s/.../exec`）を、ブラウザで開く
2. 表示の `getEffectiveUser` が、スクリプトの持ち主（デプロイを作ったアカウント）のメールアドレスであること。持ち主として実行になっていれば、誰が開いても同じになる。Web アプリは誰でも開けるので、メールアドレスは先頭 2 文字とドメインだけを出す（例 `yu***@gmail.com`）
3. `getActiveUser` は、Web アプリを開いた人が同じ組織やドメインのときだけ入り、そうでなければ空になることがある。表示のとおりに写す

別のアカウントで確かめる操作（任意）

1. 別の Google アカウント（テスト用）でブラウザにログインし、同じ URL を開く。表示が手順 2 と同じ持ち主のメールアドレスのままなら、持ち主として実行になっている
2. 編集者との違い。別のアカウントをテスト用スプレッドシートの編集者にし、そのアカウントでスプレッドシートを開いて「初期の Web アプリを作る」または「アプリを更新」を押す（デプロイの作成を、その人にさせる）。その Web アプリの URL を、持ち主のアカウントと別のアカウントで開き、`getEffectiveUser` が誰になるかを、持ち主が作った場合と比べて写す

## バージョンの数の上限

1つのプロジェクトで 200 とされる。実際に 200 個は作らない。「状態を見る」のログの「バージョンの数」を、検証を終えたあとの数と一緒に写す。資料の記述（Apps Script のクォータの資料）は、メインのセッションが `docs/to-be/spikes.md` に書く。

## ログを渡すとき

「T1-1 検証ログ」タブと、「T1-1 公開データ」タブを写して、メインのセッションに渡す。メールアドレスは伏せてよい。Web アプリの表示の `getEffectiveUser` と `getActiveUser` は、「持ち主と同じ」「別のアカウントと同じ」「空」のように書けば足りる。

## 終わった後

1. 本体のコードをテスト用スクリプトに戻す

   ```sh
   npm run push:test
   ```

   中身とマニフェストが丸ごと置き換わり、検証用のコードと権限の範囲が消える

2. 検証で作ったものを片付ける
   - リリース: `gh release delete spike-t1-1 --repo yuk-wq/ouca --cleanup-tag --yes`
   - Web アプリのデプロイ: スクリプトのエディタの「デプロイ ▸ デプロイを管理」で、検証で作ったデプロイをアーカイブする
   - 時間主導のトリガー: エディタの「トリガー」で残っていれば削除する（1回だけのトリガーは動くと消えることが多い）
   - スプレッドシートの「T1-1 検証ログ」「T1-1 公開データ」のタブは、渡した後に消してよい
   - スクリプトのプロパティ: `push:test` の後も残るので、「記録を消す」を、`push:test` の前に押しておく
